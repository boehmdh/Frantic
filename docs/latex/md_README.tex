This is a simple C++ implementation of the game "{}\+Frantic"{} by RULE FACTORY. You can read the game\textquotesingle{}s rules \href{./docs/Regeln.pdf}{\texttt{here}}. Please note that not all event cards and action cards are implemented. The game is restricted to the event cards\+: "{}\+DOOMSDAY"{}, "{}\+EARTHQUAKE"{}, "{}\+FINISH\+\_\+\+LINE"{}, "{}\+TIME\+\_\+\+BOMB"{}, "{}\+COMMUNISM"{}, "{}\+EXPANSION"{}, "{}\+THIRD\+\_\+\+TIME\+\_\+\+LUCKY"{}, "{}\+MEXICAN\+\_\+\+STANDOFF"{}, "{}\+ROBIN\+\_\+\+HOOD"{}, "{}\+MATING\+\_\+\+SEASON"{}, "{}\+FRIDAY\+\_\+\+THE\+\_\+13\+TH"{}. The action cards in the game are\+: "{}\+NONE"{}, "{}\+SKIP"{}, "{}\+REVERSE"{}, "{}\+FANTASTIC\+\_\+\+FOUR"{}, "{}\+EQUALITY"{}, and "{}\+SECOND\+\_\+\+CHANCE"{}. "{}\+REVERSE"{} has the effect of changing the turn direction as opposed to exchanging cards and "{}\+SKIP"{} skips the next player; it is not possible to choose which player is skipped. The implementation features a client/server architecture for multiplayer scenarios. It uses \href{https://www.wxwidgets.org/}{\texttt{wx\+Widgets}} for the GUI, \href{https://github.com/fpagliughi/sockpp}{\texttt{sockpp}} for the network interface, \href{https://rapidjson.org/md_doc_tutorial.html}{\texttt{rapidjson}} for object serialization, and \href{https://github.com/google/googletest}{\texttt{googletest}} for the unit tests.

First off, this project consists of a {\bfseries{server}} and a {\bfseries{client}}, each with their own main.\+cpp file.

The client renders the GUI that is presented to the player, whereas the server is a console application without a user interface. Every action a player performs in the client application (for example playing a card) is sent as a formatted message to the server application, which processes the request. ~\newline

\begin{DoxyItemize}
\item If the {\bfseries{player\textquotesingle{}s move was valid}}, the server will update the game state (e.\+g. move a card from the player\textquotesingle{}s hand to the discard pile) and broadcast this new game state to all players of the game. Whenever the client application receives a game state update, it will re-\/render the GUI accordingly and allow new interactions. ~\newline

\item If the {\bfseries{move was invalid}}, the game state will not be updated and only the requesting player will get a response containing the error message.
\end{DoxyItemize}\hypertarget{md_README_autotoc_md9}{}\doxysubsection{\texorpdfstring{4.\+2 Network Interface}{4.\+2 Network Interface}}\label{md_README_autotoc_md9}
Everything that is passed between client and server are objects of type {\ttfamily \doxylink{classclient__request}{client\+\_\+request}} and {\ttfamily \doxylink{classserver__response}{server\+\_\+response}}. Since the underlying network protocol works with TCP, these {\ttfamily \doxylink{classclient__request}{client\+\_\+request}} and {\ttfamily \doxylink{classserver__response}{server\+\_\+response}} objects are transformed into a {\bfseries{\href{https://wiki.selfhtml.org/wiki/JSON}{\texttt{JSON}} string}}, which can then be sent over the network. The receiving end reads the JSON string and constructs an object of type {\ttfamily \doxylink{classclient__request}{client\+\_\+request}} resp. {\ttfamily \doxylink{classserver__response}{server\+\_\+response}} that reflects the exact parameters that are specified in the JSON string. This process is known as {\bfseries{serialization}} (object to string) and {\bfseries{deserialization}} (string to object). If you want to read more about serialization, \href{https://en.wikipedia.org/wiki/Serialization}{\texttt{read me on Wikipedia}}.

\hypertarget{md_README_autotoc_md10}{}\doxysubsubsection{\texorpdfstring{4.\+2.\+1 Serialization \& Deserialization of messages}{4.\+2.\+1 Serialization \& Deserialization of messages}}\label{md_README_autotoc_md10}
Both, the {\ttfamily \doxylink{classclient__request}{client\+\_\+request}} and {\ttfamily \doxylink{classserver__response}{server\+\_\+response}} base classes, implement the abstract class {\ttfamily \doxylink{classserializable}{serializable}} with its {\ttfamily write\+\_\+into\+\_\+json(...)} function. It allows to serialize the object instance into a JSON string. Additionally, they have a static function {\ttfamily from\+\_\+json(...)}, which allows creating an object instance from a JSON string.

Like in most GUI environments, objects in wx\+Widgets trigger {\bfseries{events}} when they are interacted with by the user. For instance, a button will trigger a {\ttfamily wx\+EVT\+\_\+\+BUTTON} event when clicked. Similarly, a panel will trigger a {\ttfamily wx\+EVT\+\_\+\+LEFT\+\_\+\+UP} event when clicked. There are many other events that can be triggered -\/ for example when a keyboard key is pressed, when a window is resized, or when the cursor moves over an element.

In order to make the GUI interactive, we must specify the effect of an event. The easiest way is to {\bfseries{bind}} an event to a lambda function. A lambda function is an unnamed function that can be used as an r-\/value. In C++, lambda functions have the following syntax\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{[\ external\_variables...\ ](\ function\_parameters\ ...\ )\ \{}
\DoxyCodeLine{\ \ \ \ function\_body...}
\DoxyCodeLine{\}}

\end{DoxyCode}


Here is an example which binds a lambda function to a button click event\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{wxButton*\ myButton\ =\ new\ wxButton(parentPanel,\ wxID\_ANY,\ "{}Click\ me!"{});}
\DoxyCodeLine{int\ myVariable\ =\ 42;}
\DoxyCodeLine{myButton-\/>Bind(wxEVT\_BUTTON,\ [myVariable](wxCommandEvent\&\ event)\ \{}
\DoxyCodeLine{\ \ \ \ doSomething(myVariable,\ event);}
\DoxyCodeLine{\});}

\end{DoxyCode}


In C++, we need to specify which variables from outside the lambda function\textquotesingle{}s scope should be accessible within it. In the example above, {\ttfamily my\+Variable} is declared outside of the lambda function but is used by the {\ttfamily do\+Something()} function call within the lambda function. We must therefore list {\ttfamily my\+Variable} within the square brackets at the beginning of the lambda function definition, in order to make it accessible from within the lambda function\textquotesingle{}s scope.\hypertarget{md_README_autotoc_md21}{}\doxysubsubsection{\texorpdfstring{4.\+4.\+3 Positioning}{4.\+4.\+3 Positioning}}\label{md_README_autotoc_md21}
There are two ways to position elements (panels, button, etc.) within a parent element (window, panel)\+:
\begin{DoxyItemize}
\item {\bfseries{Using sizers}}\+: In this approach, you will only need to provide an element\textquotesingle{}s size, but not its position. You can then add that element to a sizer, which will then determine the element\textquotesingle{}s position based on the sizer\textquotesingle{}s predefined behavior. The most common sizer is {\ttfamily wx\+Box\+Sizer}, which allows you to position a set of elements one after the other, vertically or horizontally. You can also allow sizers to change the size of elements depending on the available space. This means you can have your GUI adapt to the size of the user\textquotesingle{}s window and/or screen.
\item {\bfseries{Using absolute positioning}}\+: In this approach, you need to provide a position (as {\ttfamily wx\+Point}) for each element. This position refers to the offset of the top-\/left corner of this element from the top-\/left corner of its parent. Using absolute positioning gives you much more control over the layout of your GUI. However, it is also much more work, as you will need to calculate the position for every single element. This is especially difficult if you want to adapt to changing window sizes.
\end{DoxyItemize}\hypertarget{md_README_autotoc_md22}{}\doxysubsubsection{\texorpdfstring{4.\+4.\+4 Classes for reuse}{4.\+4.\+4 Classes for reuse}}\label{md_README_autotoc_md22}
